- **Login** (`lib/ui/login_screen.dart`, `lib/state/robot_view_model.dart`) - editable server IP/port and operator credential fields plus `POST /api/login`; no account or password is pre-filled. A production server requires explicitly configured bootstrap credentials for its first administrator, and additional lower-privilege "operator" accounts can be created from Config > Users in the browser UI. The session token persists across launches in the iOS Keychain (`flutter_secure_storage`); the host and port are kept with `shared_preferences`. A "Scan local network" button (`lib/network/discovery.dart`) finds servers without the user needing to already know the IP.
- **Network discovery** (`lib/network/discovery.dart`) - two independent paths run at once from the "Scan local network" sheet: real mDNS/Bonjour (`discoverMdns()`, queries the `_hydra._tcp.local` service `server.ts` publishes via the `multicast_dns` package - this app is the first of the ecosystem's 3 remote clients to add it) plus a concurrent brute-force scan of `GET /api/hydra-info` across this device's own real local subnet(s) (`scanSubnets()`, derived from `dart:io`'s `NetworkInterface.list()` rather than a single hardcoded guess, since a phone's LAN is just as likely to be `192.168.0.x` or `10.x.x.x` as `192.168.1.x`, falling back to `192.168.1.x` only if interface enumeration itself comes back empty). mDNS failing quietly on an unentitled iOS build is expected (Apple's own Multicast Networking entitlement isn't granted by a plain `flutter build ios`) - the subnet scan keeps working independently either way.
- **Biometric login gate** (`lib/network/biometric_helper.dart`, `lib/ui/biometric_gate_screen.dart`) - Face ID/Touch ID/Windows Hello via `package:local_auth`, an optional `Settings` toggle that gates restoring an already-valid saved session on launch (this app never stores a raw password, only a bearer token - adapted from HYDRA-UMC-ANDROID-CONTROL's own password-refill design to that difference).
- **Atomic command sync** (`lib/state/robot_view_model.dart`'s own `_sendAtomicCommand()`) - every write (play/pause/stop/jog/valve/pump/speed/vision) uses the real `POST /api/robot/:id/command` endpoint, a small targeted payload rather than overwriting the whole settings tree, with correct combined-robot (`combinedWith`) propagation for the 5 commands that need it.
- **Live WebSocket sync** (`lib/network/hydra_websocket.dart`) - sends the token as the `hydra.bearer` subprotocol and never in the connection URL (`server.ts` refuses `/ws?token=` by default), handles both `"settings"` and `"delta"` broadcast types, auto-reconnects on drop.
- **Dashboard** (`lib/ui/dashboard_screen.dart`) - per-robot cards, reactive in real time via `Provider`'s own `ChangeNotifier`, LED convention (green pulsing = active, red solid = inactive) and combined-robot display (shown on the follower side only, resolved by id) matching HYDRA-UMC-STUDIO's own Dashboard Overview.
- **Manual Control** (`lib/ui/control_screen.dart`, `lib/ui/widgets/joystick_pad.dart`) - jog D-pad (with/without XY table target), speed/acceleration sliders, valve/pump toggles, and the global **STOP** (`lib/ui/widgets/stop_all.dart`): one tap, no long press and no confirmation, it stops every robot (`POST /api/stop-all`) and sits in the app bar of every tab, the Control tab included. The answer is shown robot by robot (a warning when a robot failed or the stop was not saved; robots reserved by someone else are marked), a network error is retried once, a server over its rate limit or without that route is answered with the per-robot stop, and when nothing answers a persistent "STOP not confirmed" banner stays until a later STOP gets an answer. The round per-robot stop keeps its long-press protection.
- **Reservations and safety limits** (`lib/ui/widgets/access_panel.dart`, `lib/models/access.dart`, `lib/network/hydra_api_client.dart`, `lib/state/robot_view_model.dart`) - The Control screen shows who holds the selected robot (nobody, this device, the same account on another device, or another account) and offers **Reserve** and **Release**, plus the list of every reservation of the server (`GET /api/claims`). The device keeps one controller id for the installation and sends it with every reserve, release, jog-arm and command (body and `X-Controller-Id` header), so a reservation belongs to the account and to this device, not to the whole account. The refusals of the server are told apart: reserved by another account, by your account on another device or window, controller id required, and jog not armed. The limits of the robot's model are read from `GET /api/safety-limits`: a jog step above the limit is not sent, and the server's warnings are shown. When the administrator requires it, an **Arm jog** button (with a countdown) must be pressed before the joystick moves the robot; the arming ends by itself, with STOP, or on release. Reservations are optional: a robot nobody reserved is commanded as before. For an **administrator** only, a **Take control** button appears on a robot someone else holds; it asks for confirmation and then reserves the robot with `force: true` (the server accepts that from administrators only and checks the role again). Writes are conditional: each one carries the revision of the robot this app last saw (`If-Match`, `lib/models/contract_v2.dart`), and when someone else changed the robot in between the server answers 412, nothing is applied, the robot is read again and the message says so (Standard checks reservations, the table and one-off commands; Strict checks everything but STOP; Off checks nothing; the choice is in the list of reservations; STOP is never checked). The XY table jog is one atomic `table` command (an older server gets the jogs it understands), the server pushes the reservations over the WebSocket so the Control screen stops polling while they arrive, and administrators read the audit record (`lib/ui/widgets/audit_dialog.dart`) with its SHA-256 chain verified twice, by the server and on the device, and can copy its lines as `.jsonl`.
- **Optional switches** - two switches, both off by default: *Block commands on saved data* (Settings) holds back every command except STOP while the screen shows the saved copy of the robot state instead of the live one, and *Do not scan mobile-data or VPN networks* (login screen) leaves those interfaces out of the subnet scan. The jog D-pad buttons are at least 44 pt and are announced by VoiceOver with their axis and direction; the camera picture is closed while the app is in the background.
- **Ask before PLAY** - on by default, turned off in Settings: before a trajectory starts the app shows the robot, its recorded points, the speed and who has it reserved (a robot reserved by someone else says the server will refuse the command). A robot that is already playing is not asked again. The choice is kept.
- **Who connects to the server:** a Connections button in the access panel opens a simple list of the apps the server has seen (kind, user, version, local network or from outside, the sessions open now, the sign-ins that worked or were refused, how long ago) and the latest sign-ins, refused sign-ins, sign-outs and ended sessions, read from the connection routes of the server. An administrator sees every entry and any other account only its own; no password or token is in either list, and an address appears only if the server was told to keep it. It says so plainly when the server is too old to offer them.
- **Access options of the server in Settings (administrators only):** an entry of Settings opens nine switches read from the server configuration: the health route without a sign-in, the announcement of the global stop, keeping the address of each client in the history of connections, the camera pictures without a ticket, a token in the WebSocket address, the blanking of secrets in the log, the signature of a spoken confirmation, the password of an IP camera handed over through the environment of its process and TLS switched on by a new installation. Each shows where its value comes from (default, saved from a screen, or fixed by the environment of the server, which locks it), only what changed is sent, every change that lowers the protection asks first, and a server that does not offer an option does not show it.
- **Bluetooth LE (GATT)** (`lib/network/hydra_ble_client.dart`, `lib/network/ble_contract.dart`, `lib/network/ble_gatt_fbp.dart`) - A real GATT client following a documented contract: scan filtered by the HYDRA service, connection with MTU negotiation, service check, notifications, framed messages in both directions, one write at a time, automatic reconnection with growing delays, the Bluetooth permission of iOS and a clear message in the user's language for every failure. **No HYDRA-UMC device implements the peripheral side yet:** the client is tested only against a simulated GATT, the Bluetooth link has never run on an iPhone, and robot commands are not sent over Bluetooth.
- **Push notifications** (`lib/network/push_bridge.dart`, `ios/Runner/AppDelegate.swift`, `lib/state/robot_view_model.dart`) - a switch in Settings, off until the person turns it on: the app asks for permission, takes the device token from the system and registers it with the server (`POST /api/push/devices`, with the language of the app), which then tells the phone through the Apple push service when a job finishes or a global stop is issued; the token is taken off the server when the switch is turned off or the person signs out. The server has them off by default. Built and tested against a fake system and a local server; no notification has reached a real iPhone, because that needs the Apple developer account described in the server documentation.
- **Global stop from outside the app** (`ios/Runner/GlobalStopShortcut.swift`, `lib/network/shortcut_bridge.dart`, `lib/state/robot_view_model.dart`) - a shortcut for the Shortcuts app, Siri, Spotlight and the Action button, and a quick action on the app icon, in the eight languages. They open the app and make the very same global stop as the STOP button (`POST /api/stop-all` with the session of the person, and the one-by-one fallback), so the contract and the handling of the token are the same; a request waits for a session for one minute at most and is dropped after that, so a stop asked for long ago never fires later. Built in CI, never run on an iPhone.
- **Camera** (`lib/ui/camera_screen.dart`, `lib/ui/widgets/mjpeg_view.dart`) - a small hand-rolled MJPEG stream parser (no third-party package), a clear "Camera Disabled" state instead of a silently blank feed, and a switch to turn a robot's vision system on/off directly from the server (`server.ts`'s `"vision"` atomic command).
- **3D View** (`lib/ui/three_d_screen.dart`) - embeds HYDRA-UMC-STUDIO's own real-time 3D viewport in a WebView (`?hideUI=true&robotId=#token=`), same approach as the Android app, for the same reason (gets the real, currently-shipping 3D scene for free). Falls back to an honest placeholder on platforms `webview_flutter` doesn't support (this repo's Windows desktop target, used for build verification).
- **System metrics** (`lib/state/robot_view_model.dart`) - `GET /api/system/metrics` polled every 5s, same cadence as the other 2 clients, shown in the Dashboard.
- **8-language UI** (`lib/l10n/`, standard `flutter gen-l10n` pipeline) - English, Spanish, French, German, Italian, Japanese, Chinese and Portuguese, matching every other client in this ecosystem. A persisted `Settings > Language` override defaults to the OS locale; `RobotViewModel.lastError` is a typed `HydraError` rather than pre-formatted English text, so business-logic error messages (login/connection/command failures) localize correctly too, not just static screen chrome.
- **Offline state cache** (`lib/network/state_cache.dart`) - the last known settings tree persists to disk (debounced 1s) alongside the real instant it was saved, so the Dashboard/Control screens show real, if possibly stale, robot data immediately on launch instead of an empty state while the live `connect()` round-trip is still in flight. A real, visible banner (not just a silent guess) says "showing cached data from HH:mm" for as long as that stays true. Superseded by the real fetch the instant it succeeds.
- **Telemetry** (`lib/ui/telemetry_screen.dart`) - a terminal-style, newest-first log of real connection/login/command lifecycle events, capped at 50 entries, with a clear-log action - same "Matrix Green" convention as HYDRA-UMC-ANDROID-CONTROL's own Telemetry tab.
- **In-App Voice Assistant** (`lib/ui/voice_assistant_dialog.dart`) - a mic icon in the app bar opens a dialog to type a question or an order, sent to `HYDRA-UMC-VOICE-UI` through the same real `POST /api/voice/turn` Server route HYDRA-UMC-ANDROID-CONTROL's own in-app voice button and paired-Watch relay use. An optional dictation (a switch in Settings, off by default) writes what you say into the text box with the Speech framework of iOS, on the iPhone itself unless you allow the online recognition of Apple; the text is never sent by itself, and only text, never audio, goes to the server. A reply never invokes a robot command directly.
- **Ecosystem tab, connection diagnostics and surfaces outside the app** (`lib/ui/ecosystem_tab.dart`, `lib/ui/connection_diagnostics_dialog.dart`, `lib/state/external_surfaces.dart`) - the Telemetry screen has an Ecosystem tab (the project manifests the server finds, with a bulb only for the services that declare one); Settings opens the connection diagnostics (scheme, how the certificate is trusted, versions, latency of a few reads of `GET /api/hydra-info`, the grade of the link and a report to copy that holds no password or token); and three switches, all off by default, turn on local notifications (a finished job, a robot offline or in safe mode, a lost connection), a Live Activity with the progress of the running trajectory and a status with a STOP request for a paired Apple Watch. The Swift parts and the sources of the Live Activity and the watch app (`ios/HydraLiveActivity`, `ios/HydraWatch`) are written but not compiled in Xcode nor tried on an iPhone or a watch, and those two extensions still need their targets in Xcode.
- **Command pipeline and reservation upkeep** (`lib/state/robot_command_repository.dart`, `lib/models/robot_command_contract.dart`, `lib/models/access.dart`) - the same split as HYDRA-UMC-ANDROID-CONTROL: one repository outside the view model keeps the revision of each robot, retries a stop when nobody answers, plays a `table` move as jogs on an older server, counts the jogs on the wire, debounces continuous commands and measures each answer, and the command names and limits are generated from `docs/robot_command_contract.json` (an identical copy of the Android file) by `tools/gen_command_contract.py`, checked by the validation. While the Control screen is open a reservation held by this device is asked for again shortly before it ends, so a long session does not lose the robot, and the reservations held by the device are released when the person signs out. The reading of the server load every few seconds rebuilds only the bar that shows it, not every screen. Built against a fake server in the tests; not run on an iPhone.
- **HOME/RESET** (`lib/ui/control_screen.dart`, `lib/util/home_reset.dart`, `lib/state/robot_view_model.dart`) - a button that takes the selected robot to its zero position through the `reset` command of the server. It is off by default: a switch in Settings turns it on and the choice is kept. It asks twice, in order and within a time limit, before anything is sent. It is refused, with a sentence of its own, when the robot is playing, in safe mode, offline or without a position, while a STOP is being sent or was not confirmed, while a jog is on the wire, when the jog must be armed and is not, and for a session that is neither operator nor administrator (the server decides the role again). The command carries a rising number like the jog, and a server that does not know `reset` is told apart and remembered. The default, the number of steps and the time limit are read from `docs/robot_command_contract.json`. Tested against a local fake server: no robot is involved.
- **Continuous jog, link health, pairing by link, alerts for the watch and Work selector** (`lib/util/dead_man_jog.dart`, `lib/network/dead_man_jog_runner.dart`, `lib/state/dead_man_jog_controller.dart`, `lib/util/pairing_link.dart`, `lib/util/watch_alerts.dart`, `lib/util/watch_relay.dart`, `lib/util/work_files.dart`) - the same as the Android app, with every number read from `docs/robot_command_contract.json`. The **continuous jog** (a switch in Settings, off by default) moves an axis while a button is held: `jogStart`, a heartbeat every 100 ms and `jogStop`; the axis is stopped (a stop sent as urgently as a STOP, tried again) on release, with STOP, when the screen is left, when the connection drops, after two missed heartbeats, after 30 seconds, when the link is bad or when the server refuses a heartbeat. A **link indicator** (on by default) shows how fast the server answers, and a second switch (on by default) blocks the continuous jog on a slow or lost link. **Pairing by link** (off by default) reads `hydra-umc://pair?host=..&port=..&fp=..&name=..`, opened by the camera of the phone or pasted in the sign-in screen or in Settings, validates it strictly, shows what it read and asks before it keeps anything; a link without the certificate fingerprint is always refused, and with it the app requires TLS and pins it. **Alerts for the Apple Watch** (a lost or restored connection, a robot offline or in safe mode, a STOP not confirmed or confirmed) are rationed and need the Apple Watch option too; the relays of the presence of the operator and of the two-step confirmation of a spoken order are off by default and wait for endpoints that the server does not have yet. The **Work selector** lists the work files of the folder of the robot and loads one with the `trajectory` command after checking its points as the server does; it never starts the playback. Written without a Mac: **not compiled in Xcode nor tried on an iPhone or a watch**; the logic is tested on the Dart VM against fake clocks, servers and bridges.
