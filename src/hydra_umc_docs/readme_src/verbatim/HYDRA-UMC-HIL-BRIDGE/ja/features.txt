* 🔑 **任意の Bearer トークン：** ループバックでは API にトークンは不要で、ループバック以外では `serve` はトークンなしでは起動しません（`--token-file` または `HYDRA_UMC_HIL_BRIDGE_TOKEN`）。トークンを設定すると、すべてのリクエストが `Authorization: Bearer <token>` を送る必要があります（一定時間での比較）。マニフェストのヘルスパスである `GET /stats` だけは開いたままです。*(実装済み)*
* 🛡️ **安全インターロック（v0）：** 実際の `route` サブコマンドは、ツインのリスクレポートが衝突切迫を示すたびに、実際のハードウェア宛てのコマンドをブロックします——今日実際に何が動くのかは下記「正直な現状確認」を参照してください。
* 🧯 **インターロックはフェイルクローズです（v0）：** `real` モードでは、経路が空いていると伝えるツインのリスクレポートがある場合にだけコマンドを転送します。レポートがなければブロックされ（省略すると以前は「衝突なし」とみなされ、ハードウェアに届いていました）、距離が NaN の場合もブロックされ、ツインが `collision_imminent` を立てていなくても余裕が 5 cm 未満ならブロックされます（`MIN_CLEARANCE_M`）。`--clear-distance メートル` で CLI に空きありのレポートを渡せます。16 KB を超えるリクエストボディは `413` で拒否されます。同じリクエストで呼び出し側が送るレポートは、ツインのトランスポートができるまでは呼び出し側の申告のままです。*（実装済み）*
* 🔏 **実機コマンドは双子が認証し、すべての指令が記録されます:** `real` モードでは、コマンドを通す報告は呼び出し側が書いたものではなくなりました。リクエストには `certificate` が含まれます。これは HYDRA-UMC-TWIN の Ed25519 鍵で、まさにその関節と位置について署名されたリスク報告です。ブリッジは公開鍵だけを持ち(`--twin-public-key-file`)、偽造されたもの、別のコマンド用のもの、2 秒より古いもの(`--certificate-max-age-ms`)、すでに使われたものを拒否します。鍵が設定されていなければ実機モードはすべてのコマンドを止め、`--allow-unsigned-risk`(試験台専用、起動のたびに表示)は呼び出し側の報告を再び信用します。実機への指令は、判断される前に必ず記録されます(`X-Hydra-Caller` からの呼び出し元、相手のアドレス、Bearer トークンの提示の有無、証明書、結果)。`--audit-log ファイル` を指定するとファイルに追記され、記録を書けない場合は指令が拒否されます。`GET /audit` は直近の記録を一覧します。固定のテストベクトル(独立した RFC 8032 実装で確認済み)を両方のリポジトリが検証します。*(実装済み、実際の双子のバイナリで試験済み、ハードウェアでは未検証)*
* ⏱️ **実機コマンドは期限付きの貸与で、期限が切れるとブリッジが自分で関節を停止します:** コマンドは `issued_at_ms`、`valid_for_ms`(最大 1000 ms、`--max-valid-for-ms`)、`seq` を持ちます。期限切れ、未来の時刻、長すぎるもの、その関節の直前より新しくないものは、証明書を消費する前にブロックされます。期限が切れるまでに新しい有効なコマンドが届かなければ、生産者が生きていてもいなくても、ウォッチドッグが関節を停止し、監査に記録し、`GET /stats` に数えます。窓のない実機コマンドは `--allow-undated-commands` を付けない限り拒否されます(起動のたびに通知)。*(記録するだけの送り先に対して実装済み、まだトランスポートなし。ハードウェアでは未検証)*
* 📐 **関節と可動範囲はロボットの URDF から読み込み、リクエストは複数のワーカーで処理します:** `serve --urdf ファイル` は、URDF にない関節、固定関節、`<limit>` の範囲外の位置に対する実機コマンドを、証明書が消費される前にブロックします(`GET /stats` の `outsideLimits`)。`serve --workers N`(既定 8)では、リクエストを途中までしか送らないクライアントが占有するのはワーカー 1 つだけでブリッジ全体ではなく、実機の指令は引き続き 1 件ずつ判定されます。*(実装済み・実機に対しては未実施)*
* 🚧 **ツインの衝突予測のシャドウ問い合わせ（既定はオフ）：** `serve --collision-shadow`（と `--twin-url`）を付けると、ブリッジは実コマンドを配信するたびに、ゾーンまたはロボット自身への接触をツインが予測するかを問い合わせ、その答えを監査ログ、`GET /stats`、ヘッダー `X-Collision-Shadow` に記録します。通知のみで、コマンドをブロックしたりインターロックの判断を変えたりすることはなく、答えのないツインは `clear` ではなく `failed` になります。実機では未検証です。
* 🌉 **双方向ブリッジ（v0、まだトランスポートなし）：** 実際のモードベースルーティング（実際/シミュレーション）と実際の無条件ミラーリングはすでに存在します。実際の HYDRA-UMC-TWIN や HYDRA-UMC コントローラーへの実際の gRPC/WebSocket 接続はまだありません。
* ⚡ **ゼロレイテンシーミラーリング（部分的）：** 実際の `mirror` サブコマンドは、今日はコマンドをメモリ内の記録用シンクへミラーリングします。実際のネットワーク接続上での「ゼロレイテンシー」はまだ今後の課題です。
* 📡 **統一プロトコル（計画中）：** 高速なローカル同期には gRPC を、リモート監視には WebSocket を使用します——意図的に、まだどのネットワークトランスポートも接続されていません（`Cargo.toml` を参照）。
* 🧪 **ハードウェアなしでテスト可能なフェイルセーフ・トランスポート（v0）：** `CommandSink::send()` は今では実際の `Result` を返し、`SimulatedTransport` はタイムアウトまたは切断されたリンクをモデル化できます。ブリッジはコマンドが実際には届いていないのに届いたと主張することは決してなく、独立した `TransportFailure` という結果を報告します——`route` の `--transport-latency-ms`/`--transport-timeout-ms`/`--transport-disconnected` で実際に発生させて確認できます。
* 🌐 **HTTP JSON API（v0）：** `serve [--addr ADDR] [--port PORT]`（デフォルト `127.0.0.1:8113`）は、同じルーティング/ミラーリングロジックを実際のブロッキング `tiny_http` サーバー経由で `POST /route`、`POST /mirror`、`GET /stats` として公開します——デプロイされた CM5 の `systemd/hydra-umc-hil-bridge.service` ユニットが実行するのと同じバイナリです（ループバックのみ）。完全なリクエスト/レスポンス契約は [`docs/CLI_REFERENCE.md`](docs/CLI_REFERENCE.md) を参照してください。

**正直な現状確認 —— 今日実際に動くもの：** `route --mode real|simulation --joint 名前 --position 値 [--collision-risk] [--distance メートル] [--transport-latency-ms MS] [--transport-timeout-ms MS] [--transport-disconnected]` は実際のルーティング判断を行います——`simulation` モードは常に送信し、`real` モードは ツインのリスクレポートが無い場合、`--collision-risk` が指定された場合、距離が NaN の場合、または余裕が 5 cm 未満の場合にコマンドをブロックする実際の安全インターロック（`--clear-distance メートル` で安全なレポートを渡せます）の対象になります。`mirror --joint 名前 --position 値` はコマンドを無条件にミラーリングします。`serve` は、一度きりの CLI 呼び出しの代わりに、両方を実際の HTTP JSON 経由でも公開します。3つとも既定ではメモリ内の受信先（`RecordingSink`、実際のコントローラーや実際の HYDRA-UMC-TWIN インスタンスではない）へルーティングされ、上記のトランスポートフラグが渡された場合は実際に失敗しうる（タイムアウト/切断）`SimulatedTransport` へルーティングされます——まだ gRPC/WebSocket トランスポートは存在しません。実際に出荷済みの内容は [`CHANGELOG.md`](CHANGELOG.md) を、すべてのコマンド/エンドポイントは [`docs/CLI_REFERENCE.md`](docs/CLI_REFERENCE.md) を、まだ残っている作業は下記のロードマップを参照してください。
