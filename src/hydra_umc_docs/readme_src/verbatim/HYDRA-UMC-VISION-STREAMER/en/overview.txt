**HYDRA-UMC-VISION-STREAMER** is intended to be the high-performance media ingestion layer of the Vision AI Node family. Its job is the low-level capture, pre-processing, and distribution of up to 8 concurrent USB 3.0 camera streams before the frames reach the Hailo-8 NPU. The pre-processing (colour-space conversion, resizing, normalisation) has no backend yet: the ISP of the Raspberry Pi 5 serves cameras on the CSI connector, not USB cameras, so for USB cameras the work would run on the CPU or on a V4L2 memory-to-memory block that has not been chosen.

**Several viewers, health and credentials:** every viewer of a camera gets every frame (the shared buffer is no longer consumed by the first reader), `GET /health` answers `200` while frames arrive and `503` otherwise (`connecting`, `stalled`, `given_up`), and if every reconnect attempt is used up the process now exits with an error instead of serving an empty stream, so its supervisor restarts it. Passwords in RTSP URLs are masked in logs and messages; pass the URL with `--device-env VAR` (an environment variable) instead of `--device` so it does not show in the process list. Hosts, devices and RTSP paths are validated before they are written into a generated pipeline, and an IP camera pipeline uses `rtspsrc` with leaky, bounded queues. Everything the streamer logs now also passes through the shared secret redaction (tokens, `password=` values and bearer headers as well as URL credentials), the same module and the same test vectors as the other projects.

This is one of the 4 children of **[HYDRA-UMC-VISION-NODE](https://github.com/JuanenRac/HYDRA-UMC-VISION-NODE)**, the family's integration parent: this project owns capture/pre-processing only, and does not run its own Hailo-8 inference, gRPC API, or safety logic - that is deliberately split across its 3 siblings.

### Key Points

* 🔑 **Optional Bearer token:** on loopback the stream needs no token; away from loopback it refuses to start without one (`--token-file` or `HYDRA_UMC_VISION_STREAMER_TOKEN`). With a token set, `/stream` must be requested with `Authorization: Bearer <token>` (constant-time comparison); only `GET /health` stays open. *(implemented)*
* ✅ **Real v0 - config, pipeline, and relay generation:** `config.py` validates a per-camera JSON config (device, resolution, fps, format); `pipeline.py` generates the exact GStreamer pipeline description for a camera; `mediamtx_config.py` generates the matching MediaMTX `paths.yml`. Exposed via `config validate`/`config gst`/`config mediamtx` below - no GStreamer runtime, V4L2, or physical camera needed to run or test any of it.
* 📷 **Real v0 - USB and RTSP IP camera capture+serve:** `mjpeg_server.py`'s `stream serve` actually opens a camera and serves real MJPEG over HTTP - a USB/V4L2 device (`--device 0`) or a real RTSP IP camera (`--device rtsp://user:pass@host:port/path`, via OpenCV's `cv2.CAP_FFMPEG` backend, no extra dependency). `config.py`'s `CameraConfig` now carries a real `source_type` (`"usb"` default, or `"ip"` with `host`/`rtsp_port`/`rtsp_path`/`username`/`password` and a real, percent-encoded `rtsp_url()` builder). Verified end to end against real hardware: all 4 real IP cameras on the local network opened and streamed real MJPEG/H.264 frames through this exact path (the 2nd pair needed their own real RTSP path, `profile0`, found on the camera's own config screen - a different path than the first pair's `/11`, not a credential or firmware issue).
* 🔁 **Real v0 - bounded buffering and reconnection:** `buffer.py`'s `FrameBuffer` is a fixed-capacity queue that drops the OLDEST frame (never the newest) once full - the real backpressure policy a live relay needs so a slow consumer can never make this process's memory grow without bound. `reconnect.py`'s `ConnectionTracker` is a real, deterministic exponential-backoff reconnect policy for a dropped camera/relay link. `mjpeg_server.py`'s own real capture path buffers a `Frame` (not just bare bytes) - a real `frame_id`/`session_id`/`capture_ts` identity, with a genuinely new `session_id` on every real reconnect, so two frames from before/after a dropped link are never conflated as one continuous stream. Exposed via `stream simulate` below - fully testable without GStreamer or a physical camera.
* 📡 **RTSP/WebRTC Support (partially planned):** the RTSP relay path (`rtspclientsink` → MediaMTX) is designed and its config is generated for real above; actually running it needs the GStreamer runtime this environment doesn't have. WebRTC output remains fully planned.
* ⚡ **Zero-Copy Pipeline (planned):** buffer handoff between V4L2 and HailoRT designed to avoid unnecessary frame copies. *(future work - needs the real V4L2/HailoRT runtime this environment doesn't have.)*
* 🔌 **HailoRT integration boundary, prepared ahead of the module:** `hailo_runtime.py` is written against the real, confirmed `hailo_platform` API (`VDevice`, `HEF`, `ConfigureParams`) - lazily imported so this repo installs/tests cleanly with no `hailort` package or Hailo-8 module present - plus real pre-flight validation that a camera's configured resolution actually matches a loaded model's input tensor shape, before a single frame is ever pushed at the device. *(implemented, integration boundary only - actually running inference and parsing a real model's NMS output is still future work.)*
* 🌈 **Pre-processing (planned, backend still to be chosen):** real-time resizing and pixel format conversion, offloading work from the CPU per frame. The ISP of the Pi 5 (PiSP) serves cameras on the CSI connector through libcamera, not USB cameras; for USB cameras the conversion would run on the CPU or on a V4L2 memory-to-memory block, which has not been investigated or chosen yet. *(future work: needs the real V4L2 runtime and a camera this environment doesn't have.)*
* 🪪 **Frame identity, latest frame and several cameras in one process:** every part of the MJPEG stream carries `X-Frame-Id`, `X-Session-Id` and `X-Capture-Ts` (milliseconds since the epoch, taken when the sensor delivered the frame), so a consumer can work out how old a frame is; `GET /latest.jpg` and `GET /latest.json` answer the newest frame and its identity and age without holding a stream open. `stream serve --config cams.json --camera NAME` takes the device, size and rate (and the RTSP credentials of an IP camera) from the list, so neither a unit file nor a process list carries them, and `stream serve-all --config cams.json --port N` serves every camera of the list from one process and one port (`/<name>/stream`, `/<name>/latest.jpg`, `/<name>/latest.json`, `/<name>/health`, `/health`) instead of an interpreter and a copy of OpenCV per camera. *(tested with fake sources; not with real cameras)*
* 🛠️ **Dynamic Configuration:** per-camera resolution, framerate, and pixel format are real and validated today (`config.py`); exposure/gain control needs the real V4L2 device and is future work.
* 🧩 **Why it exists as its own project:** capture/ISP tuning is a different skill and a different failure domain than model inference or safety logic - keeping it in its own process means a capture bug cannot take down [HYDRA-UMC-SAFETY-ZONES](https://github.com/JuanenRac/HYDRA-UMC-SAFETY-ZONES), and the two can be developed/tested independently.
* 🔐 **Detection model from verified bytes:** the Hailo detection model can be built from the bytes `HYDRA-UMC-DETECTION-HEF` already read and checked, hashed again here, and the path is never reopened; empty or different bytes are refused. *(No model has run on a Hailo chip yet.)*

**Honesty check - what actually runs today:** the config validation, GStreamer pipeline description generation, MediaMTX relay config generation, the real buffer/reconnect policy, and the HailoRT integration boundary (`config.py`, `pipeline.py`, `mediamtx_config.py`, `buffer.py`, `reconnect.py`, `hailo_runtime.py`) are real and tested ({tests} tests). `stream serve` (`mjpeg_server.py`) is the one path that does open a real camera - a USB/V4L2 device or a real RTSP IP camera - and has been verified against real IP cameras on the local network; it has not yet been verified against a physically-connected USB camera. `/stream` caps concurrent viewers at `--max-clients` (default 5, real 503 beyond that) to protect a CM5's limited Wi-Fi uplink from an unbounded number of simultaneous streams. The full GStreamer/PyGObject pipeline `config gst`/`config mediamtx` only generate the description for, and real Hailo-8 inference, still need that real runtime and a real Hailo-8 module, which this environment doesn't have. See [`CHANGELOG.md`](CHANGELOG.md) for exactly what has shipped so far, and "Current Status & Next Steps" below for what remains open. `/stream` also drops a viewer that stops reading after 30 seconds (a socket timeout), so a stalled client cannot hold one of the `--max-clients` slots forever.
