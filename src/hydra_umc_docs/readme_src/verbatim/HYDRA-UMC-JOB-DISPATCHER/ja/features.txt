* 📋 **動的キューイング：** インテリジェントなミッションの優先順位付けとスケジューリング。
* ⚖️ **工具認識ルーティング：** 正しい URTC ヘッドを持つロボットへ自動的にジョブをルーティングします。
* 🧰 **設定可能なツールカタログ（警告のみ）：** `-tools-file`（ツールヘッドの TOOL_* プロファイル名の JSON リスト）や `-tools` で、設置環境が知っているツールを宣言します。`RequiredTool` や `Tool` がカタログにないジョブ／ロボットも受け付けられ、警告が一度だけ記録されます（ツールは完全一致のため、大文字小文字だけが違う場合はヒント付き）。カタログがなければ何も変わりません。*(実装済み)*
* 🔄 **マルチステージミッション：** タスク間の依存関係を管理します（例：「ピック」は「プレース」より先に発生する必要があります）。
* 📡 **永続性：** 実際に動作するオプションの SQLite バックエンドによるミッション状態管理（`-db PATH`、`src/sqlitestore`、純粋な Go - CGO 不要） - 実際のプロセス再起動を経てもキューは生き残ることをエンドツーエンドで検証済み。未設定の場合はメモリ上のみで動作します。`GET /health` は劣化したストアを黙って失敗させず報告します。詳細は [`docs/API.md`](docs/API.md#persistence) を参照。
* 🔁 **冪等な送信（v0）：** `POST /jobs/submit` による実際の、任意の `DedupKey` ベースの重複排除——進行中または既に完了したジョブを再送信すると変更されずに返され、実際の失敗後の再試行は同じジョブ ID を再利用し、作業を二重に実行しません。優先順位の順序は繰り返し実行しても決定論的であり、明示的な回帰テストでカバーされています。
* 🧯 **デフォルトで安全。応答しなくなったロボットには仕事を渡しません（v0）：** API は指定がなければ `127.0.0.1:8090` で待ち受け、別のアドレスにはベアラートークン（`-token` / `JOB_DISPATCHER_TOKEN`。設定すると `GET /health` 以外のすべてが要求します）か、明示的な `-allow-anonymous` が必要です。HTTP サーバーにはタイムアウトがあり、64 KB を超えるリクエストボディは `413` で拒否されます。`-robot-timeout`（既定 2 分）より長く無応答のロボットには新しい仕事が割り当てられず、ジョブは優先する `location` を指定でき（`POST /jobs`、`POST /jobs/submit`。その場所のロボットが優先され、必須ではありません）、各ロボットの最後のハートビートは永続化されます（旧バージョンのデータベースはその場で移行されます）。そのため再起動しても、無応答になったロボットが見えなくなりません。*（実装済み）*
* 🗂️ **アトミックな書き込み・ページ送り・追跡可能なジョブ:** 完了・取り消し・再キュー・失効ハートビートの掃引は 1 回のトランザクションで SQLite に書き込まれます(データベースは WAL モード)。`GET /jobs` は絞り込みとページ送りができます(`status`、`limit`、`offset`、`X-Total-Count`)。各ジョブは `SubmittedAtMs`、`AssignedAtMs`、`CompletedAtMs` と、完了報告が送り返せる `Attempt` カウンター(`attempt`)を持ち、破棄された割り当ての遅れた報告は拒否されます。`DELETE /robots/{id}` はジョブのないロボットを削除します。未来の日付のロボットのハートビートは信用しません。機械可読な記述は `docs/openapi.yaml` にあります。 *(実装済み)*
* 🕒 **ジョブが待たされる理由:** `GET /dispatch/waiting` は、保留中のジョブを割り当て順に並べ、それぞれにロボットがない理由(登録されたロボットなし、そのツールを持つロボットなし、該当ロボットがすべて使用中、該当ロボットから応答がない、次の割り当てで使える空きロボットあり)を付けて返します。読み取り専用で、`POST /dispatch` はこれまでどおり割り当ての一覧だけを返します。
* ⏱️ **各ジョブの所要時間の見積もり(既定では無効):** `-eta` を付けると、`GET /dispatch/eta` が、未完了の各ジョブがいつ始まりいつ終わるか、どのロボットで行うか、キューがいつ空になるかを、同じツールの直近の完了ジョブの所要時間から見積もります(完了ジョブがない間は設定可能な既定値)。見積もれないジョブには理由が付きます。`-eta` なしではこのルートは存在せず、他は何も変わりません。読み取り専用で、注入した時計でテストしています。
* 🧾 **終了したジョブごとの生産イベント（既定ではオフ）：** `-production-events` と送り先（イベントごとに JSON 1 行なら `-production-events-file`、JSON の `POST` なら `-production-events-url`）を指定すると、ジョブ終了の報告ごとに HYDRA-UMC-SDK の共有契約の `ProductionEvent`（ロボット、終了時刻、良否、サイクル時間、ジョブ）を渡し、生産レポートがそれを OEE に変えます。イベントはまず契約と照合され、記述できないサイクルは作り出さずにスキップして記録し、送り先が失敗しても完了処理は失敗しません。スイッチがなければ何も変わらず、注入した時計でテストしています。
* 🧭 **最も近いロボット、再計画、範囲(すべて既定ではオフ):** 設定ファイル(`-config`)に調整済みの値を置き、各セクションは指定しない限りオフです。`location_costs` は場所を指定したジョブを、その場所までの宣言済みコストが最も低いロボットへ送り、`replan`(`POST /jobs/replan`、または応答しなくなった/故障したロボットでは自動)は故障したロボットのジョブを重複も欠落もなく順番どおりキューへ戻し、`eta_interval` は各見積もりに低〜高の範囲(同じツールの直近の所要時間の四分位)を添えるか、できない理由を示します。ファイルがなければ何も変わりません。注入した時計と固定シードの乱数シナリオでテスト済み。
* 📣 **ジョブのイベント：ストリームと署名付き Webhook（既定はオフ）：** 設定ファイルの `events` セクションで、`GET /events` が `assigned`、`done`、`failed`、`unknown` をサーバー送信イベントとして流します（`Last-Event-ID` 付きで再接続したクライアントは、バッファに残っている範囲で取りこぼしを受け取ります）。各 Webhook には同じイベントが HMAC-SHA256 で署名された `POST`（`X-Hydra-Signature`。シークレットは環境変数から読み、ファイルには書きません）として届き、送り先は `allowed_hosts` に載ったホストだけで、リダイレクトには従わず、再試行回数にも上限があります。イベントの発行が受信側を待つことはありません。
* 🔎 **ツールの物理的な確認（既定はオフ）：** `tool_confirmation` セクションを有効にすると、`POST /dispatch` の各パスはまず空いている各ロボットのコントローラー（ファイル内の `{robot}` を含む URL。通常はロボットのサーバー）に実際に搭載しているツールを問い合わせ、ツールを要するジョブは回答が一致するロボットにだけ渡されます。回答は `ttl_seconds` で失効し、答えないロボットは飛ばされ（`on_unconfirmed`：既定は `skip`、`allow` は申告されたツールを信用）、`GET /dispatch/waiting` は `robot_tool_not_confirmed_by_its_controller` と示します。
* 🩺 **gRPC のヘルスサービス（既定ではオフ）：** 設定ファイルの `health_grpc` セクションを有効にすると、共有 `HealthService` の `Check()` とストリーミングの `Watch()` がループバックで応答します（別のアドレスにはベアラートークンが必要）。キューが応答しストアが書き込みを受け付ける間は OK、ストアがエラーを報告したときは劣化、キューが応答しないときは異常です。接続と開いているストリームには上限があり、各ストリームはクライアントとともに終わります。本物の gRPC クライアントで本物のサーバーに対してテスト済みで、実際のウォッチドッグ、ロボット、セルに対しては一度も試していません。[`docs/HEALTH_GRPC.md`](docs/HEALTH_GRPC.md) を参照。
* 🪪 **HYDRA-UMC-SERVER の ID（既定ではオフ）:** `-identity-key-file FILE`（または `JOB_DISPATCHER_IDENTITY_KEY_FILE=FILE`）を指定すると、サービスは自身のトークンに加えて、サーバーがログイン時に発行する署名付きトークンを受け付けます。閲覧者は読み取りだけで変更はできず、資格情報のないリクエストはループバックでも拒否されます。スイッチがなければ何も変わりません。
* 🗄️ **古いジョブはアーカイブされます（データベースがあれば既定でオン）:** データベース（`-db`）を使うと、終了（完了・失敗・キャンセル）から30日以上経ったジョブは稼働中のキューから外れ、データベースに残ります。`GET /jobs?archived=1` で読み出せます（`limit`、`offset`、`X-Total-Count`）。設定ファイルの `archive` セクションで `days`（既定30、`0` でオフ）と `every_minutes`（既定60）を指定します。キュー内の別のジョブがまだ依存しているジョブは残るため、判定は変わりません。データベースがなければ何もアーカイブされません。
