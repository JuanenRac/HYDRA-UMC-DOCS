**正直な現状確認 - 今日実際に動くもの:** OPC-UA サーバーとアドレス空間のマッピング(`src/server.ts`)は本物であり、テスト済みである(`tests/server.test.ts`、`tests/security.test.ts`、`tests/security-policy.test.ts`, `tests/robotSource.test.ts`, `tests/robotSource.integration.test.ts` 全体で {tests} 件のテストが成功)。しかもこれらは本物のプロトコルレベルのテストである: `tests/server.test.ts` は本物の `OPCUAClient`(node-opcua 自身のクライアントであり、UAExpert/Ignition が使うのと同じライブラリ)を、本物のバイナリプロトコルで本物の TCP ポートに接続しており、`tests/security-policy.test.ts` は暗号化されていない `SecurityPolicy.None` セッションがデフォルトで実際に拒否されることを証明している(明示的な `OPCUA_ALLOW_INSECURE=1` という抜け道を使った場合のみ受け入れられる)。以下は偶然見つかったギャップではなく、意図的に先送りされているものである: ロボットごとのツリー（`Robot_<id>`）は HYDRA-UMC-SERVER が報告する一覧に追従する（トークンまたはアカウントで取得。`.env.example` を参照）が、アドレス空間のそれ以外の部分は起動時に一度だけ構築される。今のところエンドツーエンドでテストされているのは読み書きのみであり、OPC-UA のサブスクリプションはテストされていない。そして Pub/Sub(ロードマップのフェーズ 1)はまだ実装されていない、依存するクライアントがまだ存在しないためである。何が先送りされ、なぜそうなのかの完全なリストは `mejoras_futuras.txt` を、これまでに何が実際に出荷されたかは `CHANGELOG.md` を参照。

> **安全性とセキュリティの現状:** このエコシステムは認証された安全システムではありません。ハードウェアの E-STOP 経路、ファームウェアが強制する制限やインターロック、検証済みの動作コマンドはまだありません。ファームウェアイメージは CRC-32 と Ed25519 署名で検査し、リリースビルドは公開済みの開発用鍵を拒否します(リレーの先のツールヘッドと拡張ボードは引き続き URTC のブートローダーを使い、署名ではなく共有鍵の HMAC-SHA256 を使います)。TLS と相互 TLS は任意で、既定では無効です。独自基板はまだ実装も試験もされていません。ここに書かれた内容を人の安全のために頼る前に、[セキュリティベースライン](https://github.com/JuanenRac/HYDRA-UMC-DOCS/blob/main/docs/SECURITY_BASELINE.md)と[脅威モデル](https://github.com/JuanenRac/HYDRA-UMC-DOCS/blob/main/docs/THREAT_MODEL.md)をお読みください。
