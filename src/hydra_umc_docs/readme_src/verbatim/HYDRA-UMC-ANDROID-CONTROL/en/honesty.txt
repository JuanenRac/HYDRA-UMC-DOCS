A native Android app (Kotlin + Jetpack Compose) that controls a robot on the [HYDRA-UMC](https://github.com/JuanenRac/HYDRA-UMC) platform over Wi-Fi or Bluetooth, speaking the exact same [`REMOTE_API.md`](https://github.com/JuanenRac/HYDRA-UMC-SERVER/blob/main/docs/REMOTE_API.md) contract [HYDRA-UMC SUITE](https://github.com/JuanenRac/HYDRA-UMC-SUITE) uses - discovery, full-state read/write, and live WebSocket sync against a running [HYDRA-UMC-SERVER](https://github.com/JuanenRac/HYDRA-UMC-SERVER) backend (the same one [HYDRA-UMC STUDIO](https://github.com/JuanenRac/HYDRA-UMC-STUDIO)'s own web dashboard talks to). Direct Android counterpart to [HYDRA-UMC-IOS-CONTROL](https://github.com/JuanenRac/HYDRA-UMC-IOS-CONTROL). See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for the full design.

> **Honesty check - what actually runs today:** the core business logic - Parol6 kinematics (`kinematics/Parol6Kinematics.kt`), the settings-tree state contract (`model/HydraState.kt`), atomic command dispatch and the voice-turn relay (`viewmodel/RobotViewModel.kt`), WebSocket reconnect handling (`network/HydraWebSocket.kt`), MJPEG frame parsing (`ui/MjpegPlayer.kt`), the in-app update channel (`update/GitHubReleaseUpdater.kt`, `ReleaseMetadataParser.kt`, `SemanticVersion.kt`), and the Wear voice-relay request bookkeeping (`wear/BoundedRequestScope.kt`, `WatchCompanionProtocol.kt`) are real and covered by {tests} passing JVM/Robolectric unit tests (`./gradlew testDebugUnitTest`). What those tests structurally can't reach - and what this Windows-only dev environment has no physical Android device to verify - is `network/AuthPrefs.kt`'s real Keystore-backed `EncryptedSharedPreferences`, the `androidx.biometric` fingerprint/face prompt, `network/HydraBleClient.kt`'s Bluetooth GATT transport, and the API 28+ hardware `ImageDecoder` path in `MjpegStreamParser`: real, compiled code that hasn't been re-verified on hardware since it was written. Basic launch/login *was* confirmed live on a real device for earlier releases (see `CHANGELOG.md`'s `v0.3.2`/`v0.3.3` entries), but that predates Bluetooth, biometrics, and the hardware-decode path. See `CHANGELOG.md` for exactly what has shipped, including its own per-entry notes on what remains hardware-unverified.

> **Safety and security status:** this ecosystem is not a certified safety system. There is no hardware E-STOP path, no firmware-enforced limits or interlocks and no verified motion command yet; firmware images are checked with CRC32 and a shared-key HMAC-SHA256, not with an asymmetric signature; TLS and mutual TLS are optional and off by default; no custom board has been populated or tested yet. Read the [security baseline](https://github.com/JuanenRac/HYDRA-UMC-DOCS/blob/main/docs/SECURITY_BASELINE.md) and the [threat model](https://github.com/JuanenRac/HYDRA-UMC-DOCS/blob/main/docs/THREAT_MODEL.md) before relying on any statement here for the safety of a person.
