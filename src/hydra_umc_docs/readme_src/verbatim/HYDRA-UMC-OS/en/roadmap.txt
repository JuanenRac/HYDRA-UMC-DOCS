### Status

The base agent, its validated non-secret configuration, a hardened systemd
unit, and host-side tests are implemented. The agent is deliberately
read-only: production image assembly and CM5 hardware validation remain
separate release gates.

The installation preflight (`provisioning/preflight_cm5.py`) is proven
idempotent and side-effect-free by a real test - two consecutive runs
produce byte-identical output and touch zero files under this
repository - and a real, host-independent backup/rollback mechanism
(`provisioning/rollback.py`) protects the one system file
`install_local_agent.sh` unconditionally overwrites on every run. Both
are verified without root or a CM5 - see `tools/verify_preflight_idempotent.py`
and `tools/verify_rollback.py`.

**WiFi first-contact provisioning is real too** (`provisioning/wifi_provision.py`
/ `hydra-umc-wifi-provision.service`): a real NetworkManager AP-mode
fallback for a headless CM5 with no known network yet - brings up a real
hotspot (`nmcli device wifi hotspot`) an operator's phone/laptop can join
to submit the real target SSID/password through a small local HTTP form,
tears the AP down and joins the real network on success, restores it on
failure so the device is never stranded. The state machine is fully
unit-tested against a fake NetworkManager, including a real end-to-end
HTTP round-trip over a real loopback socket - see
`tools/verify_wifi_provision.py`. Installed by `install_cm5_base.sh` but
deliberately not auto-enabled, since it should only run on a device that really needs it: its access point password and a one-time setup code are generated for each device on its first start and read once from the journal - see `provisioning/CM5_DEPLOYMENT_SEQUENCE.md` section 3.

**Secrets are generated per device, never taken from a template.** `install_server.sh` and `install_voice_ui.sh` create their env files from the example when they are missing and replace every example value (`JWT_SECRET`, the bootstrap administrator password, the voice relay token) with a random one of this device (`provisioning/generate_secrets.py`; what the operator already chose is left alone, and the administrator password is printed once), and then refuse to go on if an example value or a short secret is left; `preflight_cm5.py` refuses a `/etc/hydra-umc/*.env` that still carries one. `install_industrial_gateway.sh` writes the secrets of the stack to `/etc/hydra-umc/gateway.env` (root only, outside the user's checkout, read by compose with `--env-file`; a `.env` left in the checkout by an earlier version is moved there) (`provisioning/gateway_env.py`: the gateway secret, and one MQTT credential and ACL rule per machine bridge). The Wi-Fi setup network no longer has a password in the source code: each device generates its own password and a one-time setup code on its first start (read once from the journal, to write on the label), the form asks for the code (locked for a minute after five wrong ones), the setup network stays open only 30 minutes after each start, and the form refuses oversized requests. Verified by `tools/verify_generate_secrets.py`, `tools/verify_gateway_env.py` and `tools/verify_wifi_provision.py`. The host name and the name of the setup network also end with six characters taken from the device (the Raspberry Pi serial number, else the MAC address), so two devices flashed from the same image no longer share a name (`provisioning/device_identity.py`, checked by `tools/verify_device_identity.py`); `HYDRA_UMC_DEVICE_SUFFIX=off` keeps the fixed names and a name you choose yourself is never changed.

**Signing keys, handed out by the installer.** The key with which the Voice UI signs the result of a confirmation (`HYDRA_UMC_VOICE_UI_RESULT_KEY`) is generated once for the device by `install_server.sh` or `install_voice_ui.sh`, whichever runs first, and written to both `/etc/hydra-umc/server.env` and `/etc/hydra-umc/voice-ui.env` (a file from an older template gets the line added), together with `HYDRA_UMC_VOICE_CONFIRM_REQUIRE_SIGNATURE=1` for the server and `HYDRA_UMC_VOICE_UI_REQUIRE_SUBJECT=1` for the Voice UI (`generate_secrets.py --ensure`; a line the operator already has, with any value, is never changed). `install_local_technician.sh` makes the key that signs the result of each tool in `/etc/hydra-umc-local-technician/result.key` (`provisioning/make_result_key.py`: 64 random hexadecimal characters, mode 0600 from the first byte, root only, never printed, never replaced once it exists, never followed through a symbolic link) and points the settings file at it; `--no-signing` (or `HYDRA_UMC_LOCAL_TECHNICIAN_SIGNING=off`) leaves the line out. No key is ever in the image or the repository, and two devices never share one. Verified by `tools/verify_result_keys.py`.

**Audit journals, on by default.** `install_local_technician.sh` switches on the technician's append-only, hash-chained audit journal and `install_node_healing.sh` the watchdog's journal (both rotated at 5 MiB, 5 files kept): what the technician was asked to do and what the watchdog decided about a node is the evidence that matters after a failure, so the installers write the setting active in a documented settings file (`/etc/hydra-umc-local-technician/local-technician.env`, `/etc/hydra-umc-node-healing/journal.env`). `--no-audit` / `--no-journal` (or `HYDRA_UMC_LOCAL_TECHNICIAN_AUDIT=off`, `HYDRA_UMC_NODE_HEALING_JOURNAL=off`) leaves a journal off and comments an active line out, never deleting what was recorded; an existing settings file is otherwise never overwritten. `tools/verify_optional_journals.py` checks the options and the names statically; nothing has been installed from them on a real CM5 yet.

**A pinned Go for the Go services.** The job dispatcher, the node watchdog and the telemetry collector are built on the device, and their `go.mod` asks for a newer Go than the `golang-go` of the Debian archive, which could not build them. Their installers now source `provisioning/go_toolchain.sh`: one upstream release from go.dev, checked against its pinned SHA-256 before it is unpacked into `/usr/local/go-<version>` (the system Go is left alone). `tools/verify_go_toolchain.py` runs the helper with a stand-in download (a good archive, a corrupted one, an already installed one) and compares the pin with the `go.mod` of the sibling projects; nothing has been installed from it on a real CM5 yet.

**One service registry.** The port, the health route and the systemd unit of every service come from `provisioning/ports.yaml` (a copy of the SDK's `contracts/ports.yaml`, generated from the project manifests). Each installer of a service ends by saying where to look once it runs, and `verify_cm5_runtime.sh --with-services` probes the health route of every running service (read-only; what is not running is skipped). `tools/verify_service_registry.py` checks the helper, the installers and the runtime check against stubs; nothing has been installed from it on a real CM5 yet.
